# ADR-031 - Supervision Circuit-Breaker as Defense-in-Depth (amends ADR-014)

**Skill:** [adr-agent](../skills/adr-agent-SKILL.md)
**Feature:** 0000018-telemetry-data-integrity
**Component:** structured-telemetry-mcp
**Date:** 2026-08-08

## Context

ADR-014 (`0000010-macos-launchd-service`) established the launchd plist and systemd unit that supervise the daemon. Design.md's P0 decision C put "supervision configuration changes" in scope for this feature, reasoning that "refuse to start" is unachievable from the daemon's exit code alone. ADR-030 (this feature) established that both platforms' *existing* configs already correctly avoid restarting a cleanly-exited (`exit(0)`) process — so the primary "stay stopped" guarantee for req-004's refuse-to-start path does not actually require a plist/unit change.

Neither existing config has any bound on *how many times* it will retry a genuinely failing process, however: macOS's plist sets no `ThrottleInterval` key at all (launchd's undocumented default applies), and the systemd unit sets `RestartSec=2` with no `StartLimitIntervalSec`/`StartLimitBurst` (confirmed absent by reading `scripts/service-linux.sh:117-118`) — so a daemon that *does* exit non-zero repeatedly (a genuine runtime crash, unrelated to req-004's refuse-to-start path, or a future bug that accidentally routes the refuse-to-start condition through a non-zero exit despite ADR-030) would still be retried indefinitely, every 2 seconds on Linux, at launchd's default cadence on macOS.

## Decision

Decision C's supervision-config deliverable remains in scope, re-framed as defense-in-depth rather than the primary mechanism (ADR-030 owns the primary mechanism):

- **macOS:** add an explicit `ThrottleInterval` key (in seconds) to the plist generated by `scripts/service-macos.sh`, long enough that a human notices repeated failures rather than launchd silently retrying in the background at its short default cadence.
- **Linux:** add `StartLimitIntervalSec` and `StartLimitBurst` to the `[Unit]` section of the systemd unit generated by `scripts/service-linux.sh`, so that after N failures within the configured window, systemd stops attempting further restarts entirely, surfacing the stopped state via `systemctl --user status` rather than retrying forever.

This applies to **ordinary crash recovery generally**, not only the refuse-to-start path — it is a general safety net for any repeated-failure scenario, consistent with decision C's original scope.

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| No supervision config change (rely solely on ADR-030's exit-zero mechanism) | Simpler; fewer moving parts | Leaves ordinary crash-loop scenarios (genuine runtime errors, or a future regression that breaks ADR-030's exit-zero contract) with no bound on retry frequency | Decision C was already human-confirmed at P0 as in-scope; dropping it here would silently narrow a confirmed decision rather than fulfilling it with corrected reasoning |
| Supervision config as the *primary* stop-the-loop mechanism (original P0 framing) | N/A — superseded by ADR-030's finding | Both configs' restart-on-failure semantics already make exit code the primary mechanism; treating config as primary was based on an incomplete reading of `launchd.plist(5)`/`systemd.service(5)` | Corrected by ADR-030; config is real but secondary |

## Affected Components

| Component | Impact |
|-----------|--------|
| structured-telemetry-mcp | `scripts/service-macos.sh` (plist generation) and `scripts/service-linux.sh` (unit generation) gain new keys; install/uninstall/status/restart command surface is otherwise unchanged |

## Consequences

**Positive:**
- Bounds retry frequency for any genuine crash loop, independent of whether the specific cause is the one ADR-030/req-004 addresses.
- Fulfils decision C's human-confirmed scope with reasoning now grounded in the actual documented semantics of both supervisors, rather than the P0-time assumption that exit code alone was insufficient.

**Negative:**
- Two more platform-specific config surfaces to keep in sync if a future feature changes supervision behavior again.
- `ThrottleInterval`'s exact value is a judgment call (no acceptance criterion pins a specific number) — set generously enough to be clearly noticeable without being so long that a quick manual restart during development feels throttled.

**Risks:**
- If `StartLimitBurst` is reached during legitimate transient conditions (e.g. a slow disk causing repeated brief failures at boot), systemd would stop retrying and require a manual `systemctl --user reset-failed` + restart — an operational wrinkle to document in the restore procedure (req-004), not a correctness risk.
