# ADR-006 - Loop Detection — Query-Side Only

## Context

User story S2 requires the human on the loop to identify where agents get stuck in a failing loop. The design defines a loop as 5+ consecutive identical `validation_failure` events within a single phase/session.

Two architectural options exist:
1. **Server-side detection**: the server watches the event stream and emits a derived `loop_detected` event when the threshold is crossed. Agents and hooks could react in real time.
2. **Query-side detection**: the server stores raw events only. The human queries for sessions exceeding the threshold after the fact.

The human explicitly chose query-side ("just log for now so we can understand the extent of the problem") as the first step — understanding the data before building reactive alerting.

---

## Decision

**Loop detection is query-side only in v1.** The server stores all `validation_failure` and `self_correction` events faithfully. The `query_telemetry` tool supports Mode B queries (REQ-003) that identify sessions where consecutive identical failures exceed 5 within a single phase.

No `loop_detected` event type is defined. No server-side state machine tracks failure sequences. The server remains a stateless append-only store.

---

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Server-side derived `loop_detected` event | Real-time signal; agents could halt automatically; hooks could notify the human | Requires the server to maintain stateful session windows; increases server complexity significantly; premature — we don't yet know how common loops are or what threshold is right | Human confirmed: understand the extent first, then react |
| Webhook / callback when threshold crossed | Decoupled alerting | Adds HTTP client logic to the server; requires configuration of a callback URL; over-engineered for a local tool | Contradicts the local stdio tool design (ADR-003) |
| Client-side loop detection (agent emits `loop_detected` itself) | Server stays simple | Requires all emitting agents to implement detection logic; duplication; not reliable | Emitting agents (0008b) cannot be assumed to implement detection |

## Affected Components

| Component | Impact |
|-----------|--------|
| structured-telemetry-mcp | No stateful session tracking; `query_telemetry` implements Mode B (consecutive failure counting via window functions); no `loop_detected` event type in the schema |

---

## Consequences

**Positive:**
- Server remains a simple, stateless append-only store — easier to reason about, test, and maintain.
- No risk of false positives from server-side detection logic.
- The human can tune the threshold (currently 5) retrospectively via query parameters without a server change.
- Understanding the extent of the problem (query-side) is the correct first step before building reactive alerting.

**Negative:**
- Loops are only visible after the fact — there is no real-time alert while the agent is running.
- The human must actively query to discover loops; they are not surfaced automatically.

**Risks:**
- If real-time loop interruption becomes a requirement, server-side detection must be added in a future pipeline run — a non-trivial change to the server's architecture (requires session state).
