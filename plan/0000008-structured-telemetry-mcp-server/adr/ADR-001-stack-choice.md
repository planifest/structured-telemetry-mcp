## Context

A stack had to be chosen before any implementation work could begin. The key constraints were:

- The server must expose MCP tools (`emit_event`, `query_telemetry`) — an MCP SDK is required.
- The server must be installable as an npm package alongside context-mode-mcp, which is already in the developer's toolchain.
- The team favours a single language across the codebase to reduce operational complexity.
- context-mode-mcp (the reference implementation) is TypeScript + Node.js — aligning with it reduces onboarding friction and allows the same build toolchain (`tsc` + `esbuild`).
- npm support is a priority: the package may be distributed via npm in a future pipeline run.

---

## Decision

Use **TypeScript** as the language, **Node.js 18+** as the runtime, and **`@modelcontextprotocol/sdk`** as the MCP framework.

TypeScript was chosen over plain JavaScript for compile-time type safety — critical for schema validation, event type discrimination, and query parameter contracts. The Google TypeScript Style Guide is enforced via ESLint.

Node.js 18+ was chosen over Bun because npm ecosystem compatibility is a stated requirement and Node.js has broader platform support for native modules (including DuckDB). Bun is a valid future option but introduces toolchain risk at this stage.

`@modelcontextprotocol/sdk` is the official SDK from Anthropic/MCP. There is no meaningful alternative for building a standards-compliant MCP server.

---

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Bun runtime | Faster startup, native TypeScript, better performance | npm native module compatibility less proven; context-mode-mcp uses Node.js | Toolchain risk outweighs performance benefit at this stage |
| Go | Better performance, compile-time safety, single binary | No idiomatic MCP SDK; team's primary language is TypeScript; breaks single-language goal | MCP SDK gap makes this impractical |
| Plain JavaScript | Simpler toolchain | No compile-time safety for schema/type contracts; Google Style Guide requires TypeScript | Type safety is a hard requirement for this domain |
| Custom MCP implementation | Full control | Significant maintenance burden; breaks compliance with MCP spec evolution | Official SDK is actively maintained by the MCP project |

## Consequences

**Positive:**
- Same language and toolchain as context-mode-mcp — developers can move between projects without context switching.
- `@modelcontextprotocol/sdk` keeps the server compliant with MCP spec changes automatically.
- TypeScript's discriminated union types map cleanly to the 9 event types.
- npm distribution is straightforward.

**Negative:**
- Node.js requires a build step (tsc + esbuild); Bun would not.
- Node.js native module support for DuckDB requires platform-specific binaries (mitigated by ADR-002's binary selection).

**Risks:**
- `@modelcontextprotocol/sdk` breaking changes in minor versions could require updates. Mitigated by pinning and CI tests.
