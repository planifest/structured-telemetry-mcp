## Context

All events must be validated at ingestion (REQ-005). The schema must also be:
- **Shareable**: 0008b (framework integration) will need to validate events before emitting them. A JSON Schema file can be bundled with the framework without depending on this server's TypeScript code.
- **Versionable**: the schema must evolve independently of the server code; `schema_version` tracks this.
- **Inspectable**: the schema is a data artifact, not just code — humans and agents should be able to read it to understand what events look like.

Two common validation approaches in the TypeScript ecosystem are JSON Schema (via `ajv`) and Zod (schema-as-code).

---

## Decision

Use **JSON Schema** (`schemas/telemetry-event.schema.json`) as the single source of truth, validated at runtime with **`ajv`**.

The schema file is the canonical artifact. TypeScript types for event payloads are derived from it (via `json-schema-to-typescript` or hand-authored types that match it). The schema file is included in the npm package's `files` array so consumers (including 0008b) can reference it directly.

Zod is not used. Zod schemas are TypeScript code — they cannot be shipped to framework integrations that may not use this server's npm package, and they cannot be introspected by non-TypeScript tooling.

---

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Zod | Excellent TypeScript DX; infers types automatically; rich error messages | Schema is TypeScript code — not shareable as a data artifact; 0008b would need to import this package just for validation | Shareability requirement rules it out |
| Zod + JSON Schema export | Best of both worlds in theory | `zod-to-json-schema` conversion is imperfect and loses some constraints; adds a build-time dependency | Source-of-truth is ambiguous (which is canonical — the Zod schema or the JSON Schema output?) |
| Hand-written TypeScript type guards | No dependencies | Verbose; no automatic error messages with field paths; maintenance burden scales with event count | Not maintainable for 9 event types with nested payloads |
| Protobuf / JSON Schema Registry | Strong schema registry story | Significant operational overhead for a local tool | Over-engineered |

## Consequences

**Positive:**
- Single artifact (`schemas/telemetry-event.schema.json`) is the contract — both server and 0008b framework integration validate against the same file.
- `ajv` compiles the schema to a validation function at startup — validation is fast (< 0.1ms per event).
- JSON Schema is language-agnostic — any future consumer can validate without depending on TypeScript.
- Schema is human-readable and self-documenting.

**Negative:**
- TypeScript types must be kept in sync with the JSON Schema manually (or via codegen). A mismatch between the schema and the TypeScript types is a silent bug risk.
- `ajv` error messages require mapping to user-friendly strings — slightly more work than Zod's built-in messages.

**Risks:**
- Schema drift: if a developer updates the TypeScript event type but forgets to update the JSON Schema (or vice versa), validation becomes inconsistent. Mitigated by a CI check that validates the schema against a set of known-good and known-bad fixtures.
