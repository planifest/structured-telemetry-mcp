## Context

The telemetry store must handle:
- High-frequency writes: every agent tool call can emit an event; a pipeline run with 200 tool calls emits 200+ events.
- Analytical queries: group-by aggregations across millions of rows, ranked results, percentile calculations (p95).
- Local operation: no separate server process; must work on the developer's machine alongside other tools.
- Long-term growth: the store should degrade gracefully toward 10M+ rows without requiring infrastructure changes.

The query patterns (group-by phase, agent, session; percentile aggregation; time-range filtering) are OLAP workloads, not OLTP. A row-oriented relational database is a poor fit.

---

## Decision

Use **DuckDB** via the **`@duckdb/node-api`** package (Node 18+ compatible, prebuilt binaries).

DuckDB is a columnar, embedded OLAP engine designed precisely for this workload: high-throughput analytical queries on append-mostly time-series data. It requires no server process, stores data in a single file, and supports SQL with window functions and percentile aggregates natively.

`@duckdb/node-api` is chosen over the legacy `duckdb` package because it ships prebuilt binaries for Windows, macOS, and Linux — eliminating native compilation as a risk on CI. WAL mode is enabled to allow safe concurrent reads while the single writer (the MCP server) is active.

---

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| SQLite (via better-sqlite3) | Battle-tested, prebuilt binaries, used by context-mode-mcp | Row-oriented; GROUP BY aggregations on 10M rows are 10-100x slower than DuckDB; no native percentile functions | Query performance does not meet scalability target at 10M rows |
| PostgreSQL | Full SQL, excellent analytics with extensions | Requires a running server process — violates local-dev-tool constraint | Not embeddable; too heavy for a local tool |
| LevelDB / RocksDB | High write throughput | No SQL query interface; would require a separate query layer | Eliminates the simplicity of direct SQL queries |
| Flat JSONL files | Zero dependencies | No aggregation; every query requires a full file scan; no index support | Cannot meet query latency targets |

## Consequences

**Positive:**
- p95 write latency target of < 5ms is achievable: DuckDB batch writes are sub-millisecond.
- GROUP BY aggregations with percentile calculations on 10M rows complete in < 2s.
- No separate server process — the developer's machine is the only requirement.
- Single-file store is easy to back up, archive, or delete.

**Negative:**
- DuckDB native module must be installed separately; the esbuild bundle cannot include it (must be `--external`).
- Prebuilt binaries increase the installed size of the npm package.
- Single-writer architecture: only the MCP server process writes; direct DuckDB client access must be read-only.

**Risks:**
- `@duckdb/node-api` API instability between minor versions (R-009). Mitigated by pinning.
- File lock contention on Windows if a DuckDB CLI is opened simultaneously (R-002). Mitigated by WAL mode and documented read-only access policy.
