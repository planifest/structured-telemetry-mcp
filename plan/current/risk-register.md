# Risk Register - Telemetry Data Integrity

**Skill:** [spec-agent](../skills/spec-agent-SKILL.md) (updated by any agent that identifies a new risk)
**Feature:** 0000018-telemetry-data-integrity
**Version:** 0.14.0
**Overall Risk Level:** medium (downgraded from high at P2 — R-001, R-005, and R-008 resolved by ADR-029, ADR-030/031, and ADR-028 respectively; R-009, the cross-platform health-check audit, is now the highest-severity open item)

## Risks

| ID | Category | Description | Likelihood | Impact | Mitigation | Status |
|----|----------|------------|------------|--------|-----------|--------|
| R-001 | technical | Backup ownership vs. DuckDB's single-writer lock is unresolved. An external scheduler cannot open `telemetry.db` while the daemon holds the write lock — the exact conflict that produced the 2026-08-03 crash loop — which appears to force the backup to run in-process, but that constrains how it can be scheduled without blocking ingestion. Independently flagged as the load-bearing unknown by three of four Scope Lock subagents. | high | high | **Resolved by ADR-029**: backup runs in-process on the daemon's own connection; no external scheduler, no second connection to `telemetry.db`. Residual: export must not starve ingestion — flagged for P4 measurement. | mitigated |
| R-002 | technical | `doctor` opens a second, independent connection to `telemetry.db` (`src/cli.ts` `runDoctor()` → `openDatabase(dbPath)`) to run its write-test check. While the daemon holds the single-writer lock, a second open by `doctor` may fail or block — confirmed by reading the existing `doctor` implementation, not merely suspected. If req-007 (backup-age reporting) tried to have `doctor` query `telemetry.db` directly for backup metadata, it would inherit this same failure mode. | high | medium | Resolved in req-007: `doctor` reads backup status from a sidecar JSON metadata file written atomically by the backup routine on each successful promote, never by opening `telemetry.db` itself. | mitigated |
| R-003 | operational | An operator can still destroy the stranded WAL data by hand. Decision D preserves the WAL by having the daemon never touch it, but the obvious, widely-suggested remedy for "database won't open" is to delete the `.wal` file — precisely what would have permanently destroyed seven weeks of events on 2026-08-03. Auto-copy-aside was considered and explicitly not chosen. | medium | high | Startup self-check message and restore documentation (req-004) must both state plainly, in the first line, that deleting the WAL is irreversible. Accepted residual risk — not eliminable without the auto-copy-aside variant the human declined. | accepted |
| R-004 | operational | A machine whose database is already poisoned gets neither a running daemon nor scheduled backups until a human intervenes, since decision D makes the daemon refuse to start. The new backup routine (req-006) never runs on exactly the machines that most need one. | medium | medium | Accepted as the cost of not silently switching a user's dataset out from under them. No mitigation beyond the startup message pointing at the restore procedure. | accepted |
| R-005 | technical | Changing the daemon's exit posture (refuse-to-start on unusable store) interacts with launchd/systemd `KeepAlive`/`Restart=on-failure` supervision (ADR-014). Exiting non-zero alone does not stop a restart loop — supervision will keep relaunching a daemon that keeps refusing. A fast exit/restart loop is itself an outage mode, potentially worse than the crash loop it replaces if not paired with the supervision config change. | medium | high | **Resolved by ADR-030 + ADR-031**: exit(0) on refuse-to-start is the primary mechanism (both `SuccessfulExit: false` and `Restart=on-failure` already respect a clean exit correctly, confirmed against source); req-005's `ThrottleInterval`/`StartLimitBurst` config remains as defense-in-depth. | mitigated |
| R-006 | operational | Events emitted while the daemon is down (refusing to start, or between deploy stop/start) are lost, not queued. Client-side buffering/retry is explicitly out of scope. The 13 dropped `context_pressure` emissions recorded in `plan/backlog/00008-daemon-durability-unreplayable-wal/evidence/` during the 2026-08-03 incident are the concrete shape of what will still happen. | high | low | None planned this feature — a cleaner, loudly-signposted refusal is strictly better than the silent data loss it replaces, but it is not less lossy. Explicitly accepted by the human at P0. | accepted |
| R-007 | security | The new backup artifact directory is a second on-disk copy of the same telemetry data as `telemetry.db` (pipeline metadata, file paths, error strings). It inherits whatever data-classification posture the live database has, but as a *new* location, it needs its own explicit ownership and permission statement so it isn't accidentally left world-readable or placed somewhere synced/backed up outside the operator's control. | low | medium | req-006 pins the backup directory under `~/.planifest/` (or the `PLANIFEST_TELEMETRY_DB` sibling path), matching the live database's existing permission model; data-contract.md documents this explicitly (see `docs/data-contract.md` §Backup Artifacts). No new exposure — same trust boundary as the existing DB file. | open |
| R-008 | technical | `EXPORT DATABASE` is assumed to survive DuckDB version changes, which is the specific property the incident's ALTER-based approach lacked. This has not been independently verified against the actual `@duckdb/node-api` 1.5.1-r.2 behaviour — it is a documented assumption, not a confirmed fact. | medium | high | **Decided by ADR-028**: `EXPORT DATABASE` (Parquet + schema.sql) chosen over a raw file copy, on documented DuckDB cross-version-migration grounds. Empirical confirmation happens naturally via req-006's mandatory verify-on-every-backup step at P3/P4 — a format problem surfaces on the first backup, not silently. | mitigated |
| R-009 | technical | The three platform deploy scripts (`service-manager.mjs`, `service-macos.sh`, `service-linux.sh`, plus a Windows path) currently duplicate the health-check logic that produced the false "Service is healthy" report — the bug lives in `verify_service()` in `service-macos.sh` specifically, with sibling implementations on the other two platforms that may or may not share the same defect. Fixing one path without auditing the others leaves the same false-positive class reachable from two of three platforms. | medium | high | req-008/req-009 require auditing all three platform paths for the same defect shape, not just fixing the one already found, per decision B. | open |

## Assumptions Logged as Risks

Documented assumptions from the specification are logged here with likelihood: medium.

| ID | Assumption | Impact if Wrong | Status |
|----|-----------|----------------|--------|
| A-001 | Single-user, localhost deployment — no multi-writer or clustered scenario to design for. | Both the no-auth assumption and the in-process backup-ownership design (R-001) would need revisiting; a second writer would defeat the single-writer lock reasoning entirely. | open |
| A-002 | `EXPORT DATABASE` is preferred over raw file copy for backups because it survives DuckDB version changes — the exact class of failure that caused the incident (see R-008). | Backups could become unreadable by exactly the mechanism this feature exists to prevent. Must be confirmed at P2 before req-006 is built against it. | open |
| A-003 | Existing developer machines may already hold a database in the poisoned-WAL state — the startup self-check (req-004) must treat this as an expected, routine case rather than an exceptional one. | If treated as exceptional/rare, the error message and recovery path may be under-tested against the one machine known to actually be in this state. | open |
| A-004 | `/health` has reported a `version` field since 0.12.0, so build-identity comparison (req-008) is possible from day one for any daemon already running 0.12.0+. | The very first deploy after upgrading past 0.12.0 cannot compare and must degrade to a warning rather than a false pass — req-008 must handle this explicitly, not assume every daemon in the field already reports build identity. | open |
