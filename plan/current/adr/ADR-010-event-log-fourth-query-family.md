# ADR-010 - event_log as a Fourth Distinct Query Family

## Context

FEA-001 requires a new `mode: "event_log"` query that returns the complete raw event stream for a session or initiative. The existing query dispatch in `src/server-factory.ts` routes to one of three families:

- **Bottlenecks** — any query with a `group_by` field
- **Failures** — `mode` in `['retry_summary', 'loop_candidates', 'failure_sequence', 'failure_cluster']`
- **Token efficiency** — `mode` in `['context_pressure', 'mcp_impact', 'request_volume', 'trend', 'drill_down']`

The question is whether `event_log` should be added as a new mode inside one of the existing families (most likely token efficiency or failures), or implemented as a new fourth dispatch branch with its own `IQueryService` method and source file.

---

## Decision

`event_log` is implemented as a **new fourth query family**: a new `src/query/event-log.ts` file, a new `EventLogQuery` interface, and a new `eventLog()` method on `IQueryService`. The `dispatchQuery` function gains a fourth branch for `mode === 'event_log'`, checked before the existing three branches.

This is decided because:

1. `event_log` has fundamentally different semantics from all three existing families — it returns raw events in insertion order, not aggregates. Adding it to failures or token efficiency would pollute those families with non-aggregate logic.
2. `event_log` requires its own WHERE clause logic (`session_id` OR `initiative_id` with AND intersection) that does not share patterns with the existing `buildWhereClause` implementations.
3. Giving it a dedicated file and interface keeps the query service contract explicit and testable in isolation.
4. The dispatch check (`mode === 'event_log'`) placed before the existing checks ensures no ambiguity — it cannot accidentally match an existing family's routing condition.

**Scope parameter semantics:** When both `session_id` and `initiative_id` are provided, AND logic (intersection) is applied. This is more restrictive and prevents unexpectedly large result sets. OR logic would require UNION or complex WHERE, adds complexity, and the more common use case is narrowing scope, not broadening it.

**Default limit:** 100 rows when `limit` is omitted. Unbounded queries are not supported.

---

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Add `event_log` as a mode inside token efficiency | No new file or interface | Semantically wrong — token efficiency aggregates, event_log returns raw rows; pollutes the family | Rejected on semantic grounds |
| Add `event_log` as a mode inside failures | `failure_sequence` is the closest analogue | Failures family filters by event type; event_log returns all types — fundamentally different contract | Rejected on semantic grounds |
| Single monolithic query file | Simpler dispatch | Single file grows unbounded; hard to test families in isolation | Rejected — established pattern is one file per family |

## Consequences

**Positive:**
- `event_log` semantics are explicit and independently testable
- `IQueryService` contract clearly documents four distinct query capabilities
- Future query families follow the same pattern without modifying existing families

**Negative:**
- One additional file and interface to maintain
- `IQueryService` grows by one method — any mock implementation must add `eventLog()`

**Risks:**
- If the `event_log` dispatch branch is placed after the existing bottleneck check, it will never be reached (bottleneck check matches any query with a `group_by` field; event_log has no `group_by`). Must be placed before existing checks or as a named `mode` check first.
