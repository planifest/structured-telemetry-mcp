# ADR-011 - Validate-and-Throw for Required session_id Parameters

## Context

BUG-002 and BUG-003 document that `failure_sequence` and `drill_down` both use the pattern `query.session_id ?? ''` when dispatching. When `session_id` is omitted, the SQL `WHERE session_id = ''` returns zero rows — no error, no indication of a malformed query. Callers receive a false "no data" signal.

The question is how to fix this: should the code return a structured error response, throw an exception, or add a validation layer upstream (e.g., at the Zod schema level in `dispatchQuery`)?

---

## Decision

Both dispatch sites are changed to **validate and throw** `Error('failure_sequence requires session_id')` and `Error('drill_down requires session_id')` respectively when `session_id` is absent or an empty string.

The thrown error propagates through `dispatchQuery` to the MCP tool handler in `createQueryTelemetryHandler`, which already wraps dispatch in a try/catch and returns `{ ok: false, error: e.message }` to the caller. No new error handling infrastructure is needed.

This is decided because:

1. The existing error handling path in `createQueryTelemetryHandler` already handles thrown errors — using it is consistent and requires no new abstraction.
2. Upstream Zod validation at the schema level would require adding `session_id` as a required field on these specific modes, which complicates the single flat Zod schema that currently validates all query shapes uniformly.
3. A structured error response returned from the query function itself (rather than thrown) would require adding a discriminated union return type to `IQueryService` — a larger change with more downstream impact.
4. Throwing is idiomatic for "contract violation" errors in this codebase — the existing exhaustive switch in `resolveGroupColumn` implicitly throws via TypeScript's never type for unrecognised values.

The fix also removes the `?? ''` fallback entirely — empty string is treated the same as absent (both throw).

---

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Upstream Zod validation on query shape | Catches error before dispatch | Requires conditional required fields in Zod schema per mode — complex; Zod v4 discriminated unions add boilerplate | Rejected — disproportionate complexity for two dispatch sites |
| Return `{ ok: false, error }` from query function | Explicit return type | Changes `IQueryService` return type from `Promise<QueryResponse>` to `Promise<QueryResponse \| ErrorResponse>` — affects all callers and mocks | Rejected — broad interface change for a targeted bug fix |
| Keep `?? ''` but log a warning | Non-breaking | Silent failure remains; logs may be missed | Rejected — the bug is the silence; a warning does not fix it |

## Consequences

**Positive:**
- Callers can now distinguish a malformed query (error response) from a genuinely empty session (empty result set)
- The fix is contained — no interface changes, no new abstractions
- Error message is explicit and actionable: agents calling without `session_id` will see exactly what is missing

**Negative:**
- Any caller currently relying on the silent empty-result behaviour will now receive an error response instead. This is a breaking behaviour change — intentional, as the previous behaviour was a bug.

**Risks:**
- If existing integration tests assert `failure_sequence` returns an empty array when called without `session_id`, those tests will fail and must be updated to assert an error response. This is expected and desirable.
