## Context

There are 9 event types, each with a different typed `data` payload (see REQ-005 and the data contract). The storage schema must accommodate:
- All 9 event types in a queryable form.
- Future event types without requiring schema migrations.
- Efficient GROUP BY queries on envelope fields (event, phase, session_id, agent, timestamp).
- Drill-down access to the raw `data` payload for debugging.

Two main approaches exist: a single polymorphic table or a typed table per event.

---

## Decision

Use a **single `events` table** with a **`data` JSON column** for the typed payload.

The common envelope fields (`event`, `session_id`, `phase`, `agent`, `tool`, `model`, `mcp_mode`, `timestamp`) are stored as typed columns and indexed. The event-specific payload is stored in the `data` JSON column.

DuckDB's `json_extract` and `->` operator allow efficient extraction of JSON fields in queries. This means bottleneck queries (group by phase, agent) operate on indexed columns and never touch `data`; drill-down queries extract specific fields from `data` for the matching rows.

Adding a new event type requires only a new JSON sub-schema — no table migration.

---

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| One table per event type (e.g. `phase_start_events`, `validation_failure_events`) | Full column-level typing; no JSON extraction | 9 tables to maintain; cross-event queries require UNION ALL; adding an event type requires a migration; query layer complexity multiplied by 9 | Schema complexity outweighs typing benefit; JSON extraction in DuckDB is fast |
| EAV (entity-attribute-value) | Flexible | Notoriously poor query performance; difficult to reconstruct full events | Rejected immediately — wrong pattern for analytical workloads |
| Single table, all payload fields as nullable columns | Full column-level typing; no JSON | ~40 nullable columns; sparse columns waste columnar storage; every new event type adds columns; migration required | Column explosion; harder to evolve |

## Consequences

**Positive:**
- All bottleneck and aggregation queries operate on indexed envelope columns — no JSON parsing in the hot path.
- Adding a new event type is a schema validation change only — no DuckDB migration.
- Drill-down queries (Mode E in REQ-004) return the raw `data` column directly — no reconstruction.
- DuckDB's columnar storage is efficient for the sparse JSON column (most rows only query envelope fields).

**Negative:**
- Payload field queries (e.g. filter by `data.failure_type`) require `json_extract` — slightly slower than a typed column index.
- No database-level enforcement of payload shape — validation is the application's responsibility (REQ-005).
- If a payload field needs an index for performance, it must be a computed/virtual column.

**Risks:**
- Schema evolution risk (R-003): if a payload field is renamed across schema versions, queries must handle both names. Mitigated by `schema_version` column and null-coalescing in the query layer.
