# Quirks — structured-telemetry-mcp

## 0000010-macos-launchd-service

- **No automated TDD for the macOS/Linux service scripts.** `plan/current/design.md`'s declared testing strategy for Scope A is manual (`launchctl list`/`systemctl --user status`, `curl /health`, reboot/logout survival check) — there is no shell-script test harness in this repo. `req-001`–`req-008` were implemented directly (dispatched to parallel sub-agents) rather than through the mandatory TDD red→green→refactor sub-agent loop that `req-009`–`req-012` (TypeScript) went through. Documented deviation, not an oversight.
- **`getting-started.md`/`mac-setup.md` don't exist.** `req-004`/`req-008` assumed these files already documented the Windows service alongside which macOS/Linux would be added — they don't exist anywhere in this repo, and the Windows `service.ps1` was entirely undocumented before this feature. Resolved by adding a new "Background Service" section to `README.md` covering all three platforms instead of inventing new top-level files.
- **`scripts/service-linux.sh` is untested against real systemd hardware.** No Linux machine was available during this feature's implementation (see `linux-systemd-reference.md`). Tracked as risk-register R-002 — must be verified on at least one real systemd distro before this is considered done.

## Pre-existing (surfaced by P4's library audit, not introduced by 0000010)

- **`ajv` (direct) is used for wire-schema validation**, which `planifest-framework/standards/library-standards/typescript/prefer-avoid.md` lists as avoided in favour of `zod`. This is a deliberate, documented exception: ADR-005 (`plan/_archive/0000008-mcp-server-foundation-2026-04-19/adr/`) chose JSON Schema/`ajv` specifically because the schema must be shareable with the sibling `planifest-framework` repo without a TypeScript dependency — Zod schemas are TypeScript code and cannot be introspected by non-TypeScript tooling. ADR-013 (this feature) builds on and reaffirms that boundary rather than reopening it — Zod is used only as an MCP tool-argument gate, not as a wire-schema replacement.

## 0000012-test-harness-and-sdk-audit

- **1 residual low-severity `npm audit` finding, accepted as out of scope.** `tsx`'s own nested `node_modules/tsx/node_modules/esbuild` carries a Low-severity Windows-only dev-server arbitrary-file-read advisory (GHSA-g7r4-m6w7-qqqr). `npm audit fix` (no `--force`) resolved everything else this feature targeted (hono, fast-uri, ip-address, qs, express-rate-limit — all transitive via `@modelcontextprotocol/sdk`'s `@hono/node-server` dependency, all 3-5 advisories from `0000011`'s deferred backlog item). This one is pinned by `tsx`'s own `package.json` and only fixable via `--force` (a potentially-breaking `tsx` major bump) or waiting for upstream. `tsx` is a devDependency (local `npm run dev`/`setup`/`doctor` convenience only — never shipped in the production bundles), and the advisory only fires when running esbuild's own dev server on Windows, which this repo never does. Accepted risk; not re-filed to the backlog given the low severity and narrow blast radius — revisit only if `npm audit` escalates its severity or `tsx` ships a fix.

## 0000013-group-by-validation-fix

- **`dispatchQuery`'s `mode`-based branches validated their values against a fixed allow-list from day one; the `group_by` branch didn't.** Only `typeof q['group_by'] === 'string'` was checked — any string reached `qs.bottlenecks()`, and an invalid one (e.g. `event_type`, a real column but not a valid `group_by` dimension) fell through `resolveGroupColumn()`'s switch with no `default` case, producing `undefined`, which got string-interpolated straight into the SQL `GROUP BY` clause. DuckDB's resulting syntax error surfaced to MCP callers as an opaque `"backend query failed: 400"` with the real cause lost. Fixed by validating against `BOTTLENECK_GROUP_BY_VALUES` (now exported from `bottlenecks.ts` as the single source of truth) before dispatch, mirroring the `mode`-branch pattern. **Worth checking for this same asymmetry (unchecked string reaching a query builder's internal switch/map) if a future query family adds its own enum-like parameter** — it's an easy validation gap to reintroduce one family at a time.
- **`HttpQueryService.post()` (`src/http-query-service.ts`) discards the daemon's actual error body on a non-2xx `/query` response**, replacing it with a generic `` `backend query failed: ${res.status}` ``. Found while verifying this fix: since `dispatchQuery` runs client-side in the stdio process *and* server-side again inside `server-http.ts`'s `/query` handler (double-dispatch — ADR-009's proxy design), any case where the client-side check is stale or bypassed and the daemon rejects the request server-side loses the daemon's specific, useful error message and re-surfaces the same class of opaque-400 problem this fix just closed for `group_by` specifically. Not fixed here (out of scope for this change — narrow interpretation, `group_by` validation only); worth a small follow-up to have `post()` parse and forward the daemon's `errors` array from the response body instead of just the status code.
- **Rebuilding and redeploying the daemon (`npm run deploy`) does not refresh already-spawned stdio MCP client processes.** Each agent tool (Claude Code, Cursor, etc.) with this server registered spawns its own long-lived `server.bundle.mjs` process at MCP connection time; that process holds the old code in memory regardless of what's on disk. `npm run deploy` only manages the systemd/launchd-supervised HTTP daemon (`server-http.bundle.mjs`). A connected agent session must be restarted (reconnect the MCP server / restart the tool) to pick up a code change — same underlying fact as R-004 (AJV recompilation), one layer further out at the client-proxy boundary.
