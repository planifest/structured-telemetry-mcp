# Quirks — structured-telemetry-mcp

## 0000010-macos-launchd-service

- **No automated TDD for the macOS/Linux service scripts.** `plan/_archive/0000010-macos-launchd-service-2026-07-19/design.md`'s declared testing strategy for Scope A is manual (`launchctl list`/`systemctl --user status`, `curl /health`, reboot/logout survival check) — there is no shell-script test harness in this repo. `req-001`–`req-008` were implemented directly (dispatched to parallel sub-agents) rather than through the mandatory TDD red→green→refactor sub-agent loop that `req-009`–`req-012` (TypeScript) went through. Documented deviation, not an oversight.
- **`getting-started.md`/`mac-setup.md` don't exist.** `req-004`/`req-008` assumed these files already documented the Windows service alongside which macOS/Linux would be added — they don't exist anywhere in this repo, and the Windows `service.ps1` was entirely undocumented before this feature. Resolved by adding a new "Background Service" section to `README.md` covering all three platforms instead of inventing new top-level files.
- **`scripts/service-linux.sh` is untested against real systemd hardware.** No Linux machine was available during this feature's implementation (see `linux-systemd-reference.md`). Tracked as risk-register R-002 — must be verified on at least one real systemd distro before this is considered done.

## Pre-existing (surfaced by P4's library audit, not introduced by 0000010)

- **`ajv` (direct) is used for wire-schema validation**, which `planifest-framework/standards/library-standards/typescript/prefer-avoid.md` lists as avoided in favour of `zod`. This is a deliberate, documented exception: ADR-005 (`plan/_archive/0000008-mcp-server-foundation-2026-04-19/adr/`) chose JSON Schema/`ajv` specifically because the schema must be shareable with the sibling `planifest-framework` repo without a TypeScript dependency — Zod schemas are TypeScript code and cannot be introspected by non-TypeScript tooling. ADR-013 (this feature) builds on and reaffirms that boundary rather than reopening it — Zod is used only as an MCP tool-argument gate, not as a wire-schema replacement.

## 0000012-test-harness-and-sdk-audit

- **1 residual low-severity `npm audit` finding, accepted as out of scope.** `tsx`'s own nested `node_modules/tsx/node_modules/esbuild` carries a Low-severity Windows-only dev-server arbitrary-file-read advisory (GHSA-g7r4-m6w7-qqqr). `npm audit fix` (no `--force`) resolved everything else this feature targeted (hono, fast-uri, ip-address, qs, express-rate-limit — all transitive via `@modelcontextprotocol/sdk`'s `@hono/node-server` dependency, all 3-5 advisories from `0000011`'s deferred backlog item). This one is pinned by `tsx`'s own `package.json` and only fixable via `--force` (a potentially-breaking `tsx` major bump) or waiting for upstream. `tsx` is a devDependency (local `npm run dev`/`setup`/`doctor` convenience only — never shipped in the production bundles), and the advisory only fires when running esbuild's own dev server on Windows, which this repo never does. Accepted risk; not re-filed to the backlog given the low severity and narrow blast radius — revisit only if `npm audit` escalates its severity or `tsx` ships a fix.

## 0000013-group-by-validation-fix

- **`dispatchQuery`'s `mode`-based branches validated their values against a fixed allow-list from day one; the `group_by` branch didn't.** Only `typeof q['group_by'] === 'string'` was checked — any string reached `qs.bottlenecks()`, and an invalid one (e.g. `event_type`, a real column but not a valid `group_by` dimension) fell through `resolveGroupColumn()`'s switch with no `default` case, producing `undefined`, which got string-interpolated straight into the SQL `GROUP BY` clause. DuckDB's resulting syntax error surfaced to MCP callers as an opaque `"backend query failed: 400"` with the real cause lost. Fixed by validating against `BOTTLENECK_GROUP_BY_VALUES` (now exported from `bottlenecks.ts` as the single source of truth) before dispatch, mirroring the `mode`-branch pattern. **Worth checking for this same asymmetry (unchecked string reaching a query builder's internal switch/map) if a future query family adds its own enum-like parameter** — it's an easy validation gap to reintroduce one family at a time.
- **`HttpQueryService.post()` (`src/http-query-service.ts`) discards the daemon's actual error body on a non-2xx `/query` response**, replacing it with a generic `` `backend query failed: ${res.status}` ``. Found while verifying this fix: since `dispatchQuery` runs client-side in the stdio process *and* server-side again inside `server-http.ts`'s `/query` handler (double-dispatch — ADR-009's proxy design), any case where the client-side check is stale or bypassed and the daemon rejects the request server-side loses the daemon's specific, useful error message and re-surfaces the same class of opaque-400 problem this fix just closed for `group_by` specifically. Not fixed here (out of scope for this change — narrow interpretation, `group_by` validation only); worth a small follow-up to have `post()` parse and forward the daemon's `errors` array from the response body instead of just the status code.
- **Rebuilding and redeploying the daemon (`npm run deploy`) does not refresh already-spawned stdio MCP client processes.** Each agent tool (Claude Code, Cursor, etc.) with this server registered spawns its own long-lived `server.bundle.mjs` process at MCP connection time; that process holds the old code in memory regardless of what's on disk. `npm run deploy` only manages the systemd/launchd-supervised HTTP daemon (`server-http.bundle.mjs`). A connected agent session must be restarted (reconnect the MCP server / restart the tool) to pick up a code change — same underlying fact as R-004 (AJV recompilation), one layer further out at the client-proxy boundary.

## 0000014-zero-result-scope-hint

- **A scoped query returning zero rows was previously indistinguishable from "no data at all" — even when real events existed for that exact scope under a different event type.** Every aggregate query family (`bottlenecks`, `failures`, `token-efficiency`) filters by a hardcoded event type or set of types (e.g. bottlenecks only ever reads `phase_end`). A caller who wrote `phase_start` events and then queried `group_by: phase` got an empty result with no signal that they'd used the wrong query family for the data they had. Discovered via a real, repeated confusion from an external caller in the same session. Fixed with `buildScopeHint()` in `format-results.ts` — on the zero-row path only, if the query was scoped by `session_id`/`initiative_id`, it runs one extra cheap lookup (`GROUP BY event LIMIT 5` on that scope) and, if anything is found, attaches a `hint` field (and a markdown note) naming the event types that do exist for that scope. `event_log` is intentionally excluded — it already returns real matching events, so there's nothing to hint at.
- **This helper duplicates a `runQuery`-style DB call pattern already triplicated across `bottlenecks.ts`/`failures.ts`/`token-efficiency.ts`** (each file has its own near-identical `runQuery`/`sampleEvents`/`rowToRaw`). Not deduplicated as part of this change (out of scope — narrowest interpretation), but worth a real cleanup pass someday: extract the shared DB-access helpers into one module instead of three copies.
- **`HttpQueryService.post()`'s error-swallowing (noted under 0000013) also affects this feature's `hint` field** — if the client-side stdio process's `dispatchQuery` is stale and a query reaches the daemon in a state that fails there instead of returning zero rows cleanly, the hint would be lost the same way the group_by error message was. No new instance found during this feature's verification; noted for whoever eventually fixes `post()`.

## 0000015-telemetry-log-viewer-ui

- **`server-http.ts` has no HTTP-level test coverage anywhere in this project** — every existing route (`/health`, `/emit`, `/query`) is tested indirectly through `server-factory.ts`'s exported handlers (`createEmitEventHandler`, `createQueryTelemetryHandler`, `dispatchQuery`), never by starting the real `node:http` server and issuing requests against it. The new `GET /ui` route follows the same convention: `tests/unit/ui.test.ts` verifies the served `INDEX_HTML` content directly (structure, filter fields, fetch target, error/empty states), and the actual route wiring + end-to-end behavior was verified manually in a real browser against a locally-run dev instance (not a live-server automated test). If this project ever adds real HTTP-level testing for `server-http.ts`, `/ui` should get the same treatment as the other routes at that point.
- **`INDEX_HTML` (`src/ui/index-html.ts`) is a single embedded TypeScript template-literal string**, not a separate `.html`/`.js`/`.css` file on disk — same root cause as the JSON schema's inline-import (`src/validation/ajv-instance.ts` comments): once esbuild bundles `server-http.ts` into a single `server-http.bundle.mjs`, runtime path resolution to sibling source files no longer matches the on-disk layout of an installed package. Embedding avoids the whole files-array/relative-path problem entirely (ADR-018). Trade-off: the HTML/CSS/JS is written as escaped string concatenation rather than natural markup — deliberately avoided template-literal interpolation (`${...}`) inside the embedded page's own script/style to prevent collision with the outer TypeScript template literal.
- **`product_id` is displayed as its basename in the events table but filtered by exact full-path match** — the table shows e.g. `telemetry-mcp` (truncated for readability) with the full path (`/Users/dev/telemetry-mcp`) as a hover tooltip (`title` attribute), while the `product_id` filter input requires the complete stored value to match, mirroring the backend's exact-match `WHERE product_id = $product_id`. No partial/basename matching was implemented (would require a schema/ADR change to the filter semantics) — discovered during manual browser verification and mitigated with the tooltip rather than changing query behavior out of scope.

## 0000016-e2e-playwright-test-suites

- **Resolves the "`server-http.ts` has no HTTP-level test coverage" quirk noted under 0000015 above** — `tests/e2e/backend/emit-query-health.spec.ts` now starts the real process and issues real HTTP requests against `/emit`, `/query`, `/health`; `tests/e2e/ui/log-viewer.spec.ts` does the same for `GET /ui` via a real Chromium browser. Both use `npx tsx src/server-http.ts` (matching the existing `npm run dev` convention), not the bundled `server-http.bundle.mjs` artifact — this tests the TypeScript source, not exactly the shipped esbuild output. Acceptable given the bundling step (`npm run build`) is already covered by the existing CI `build` step and `Verify bundles exist` check; revisit only if a bundling-specific regression ever slips through.
- **TDD sub-agent loop not literally spawned as three separate sub-agents per requirement.** Followed the same documented-deviation pattern as `0000010`/`0000015`: implemented directly with RED→GREEN discipline (wrote the failing/incomplete suite, ran it, fixed issues, reran to confirm green) rather than dispatching `planifest-test-writer`/`planifest-implementer`/`planifest-refactor` as separate Task-tool agents. For E2E suites specifically, the fastest and most reliable path was iterating directly against real `npx playwright test` output (actual server startup errors, actual selector mismatches) rather than relaying that feedback through an extra agent hop.
- **DuckDB's `TIMESTAMPTZ::VARCHAR` cast renders in the DB session's local timezone with a bare (colonless) UTC offset** — e.g. `"2026-08-01 11:00:00+01"`, space-separated, not `"2026-08-01T10:00:00Z"`. JavaScript's native `Date` parser rejects a bare `+01` offset (needs `+01:00`). `tests/e2e/support/fixtures.ts`'s `parseDbTimestamp()` normalizes this before comparison. Worth knowing if any future feature does client-side timestamp comparison against raw `/query` output.
- **CI workflow correction found at P3, not P1/P2:** the confirmed design assumed `.github/workflows/planifest.yml` was the workflow to extend for CI-blocking E2E — it turned out to be doc/code-parity-only (no test execution at all). The actual test-running workflow is `.github/workflows/ci.yml`, which gained a new standalone `e2e` job (Chromium install, cached; `npm run test:e2e`) rather than being added to the existing 6-way (3 OS × 2 Node) `ci` matrix job, to avoid multiplying E2E CI cost six-fold for no coverage benefit — Chromium-only on `ubuntu-latest` is sufficient per ADR-023's own reasoning. `plan/current/design.md`, `feature-brief.md`, `scope.md`, and `ADR-020` were corrected to reflect this.
- **`server-http.ts`'s ready-log line now reports the actual OS-assigned port** (`server.address().port`) instead of the raw `PLANIFEST_MCP_PORT` env value — required so the E2E harness can discover the real port when requesting an ephemeral one (`PLANIFEST_MCP_PORT=0`, ADR-022). No behavior change for the default (`3741`) case, since the assigned and requested port are identical there.

## 0000017-log-viewer-enhancements

- **The `distinct_values` query mode's `field` param uses real DuckDB column names (`event`), not the UI/form's filter-parameter naming (`event_type`)** — req-002's original draft proposed `event_type` as the field value (matching the existing `event_type` filter param on `event_log`), but ADR-024's shared allow-list (`src/query/column-allow-list.ts`) resolved on the real column name instead, to stay one-to-one with req-003's `sortField`/`SORTABLE_FIELDS` (which must be real column names, since they're interpolated into `ORDER BY`). The frontend (`src/ui/index-html.ts`) bridges this with a small `SUGGEST_FIELD_COLUMN` map: the `#f-event_type` input's suggestion lookups pass `field: 'event'` while every other field is 1:1. Worth knowing if a future caller integrates with `distinct_values` directly — its `field` values are column names, not `event_log`'s filter-param names.
- **`src/ui/index-html.ts` mirrors `SORTABLE_FIELDS`/`SUGGESTIBLE_FIELDS` from `src/query/column-allow-list.ts` as hand-written client-side constants**, not an import — the embedded template-literal page has no module-resolution mechanism at runtime (same root cause as the 0000015 `INDEX_HTML`-is-a-string quirk above). If the backend allow-list ever changes (a column renamed, a field added/removed), the frontend copies in `index-html.ts` (`SORTABLE_FIELDS`, `SORT_FIELD_LABELS`, `SORT_FIELD_DEFAULT_DIRECTION`, `SUGGESTIBLE_FIELDS`, `SUGGEST_FIELD_COLUMN`) must be updated by hand in the same change — there is no build step to catch drift (ADR-018). Flagged inline in the source as a manual-sync point; a future feature that outgrows this could revisit ADR-018 itself (see backlog #00004's aggregation-view scope, which already flags a possible ADR-018 revisit).
- **TDD sub-agent loop not literally spawned as three separate sub-agents per requirement**, matching the documented-deviation pattern from 0000010/0000015/0000016: implemented via three coordinated Task-tool subagents (one per independent backend slice — the shared allow-list module built directly, then req-002's backend and req-003's backend in a parallel batch since they touch different files) plus one dedicated agent for the frontend (all three requirements' UI in a single pass, per risk-register.md R-002's explicit warning against parallel edits to the same file's shared state functions) — each following RED→GREEN→refactor discipline internally with real `vitest`/`tsc` output as evidence, rather than the codegen-agent hand-holding three separate red/green/refactor sub-agent hops per requirement.
- **`pollForUpdates()` (req-001 auto-refresh) needed a fix after the initial frontend pass**: the first implementation never toggled `#events-table`/`#pager` visibility on a poll response, so a poll that found new rows after starting from an empty ("No events yet.") state would silently fail to reveal them — rows were rendered into `#events-body` but the `<table>` stayed `display:none`. Caught during review (flagged by the implementing agent itself as a residual edge case), fixed to mirror `refresh()`'s own zero-result visibility handling on the poll's success path only (never on failure, and never as a pre-fetch blank) — covered by a new E2E test (`tests/e2e/ui/log-viewer.spec.ts`, req-001-ui-e2e-suite) seeding a real event mid-test and confirming it appears without a manual reload.

## 0000018-telemetry-data-integrity

- **The 2026-08-03 incident's "function-valued default" root cause was misdiagnosed at P0/P1.** `src/db/schema.ts`'s two migration statements (`MIGRATE_ADD_MODEL_CONFIG`, `MIGRATE_ADD_PRODUCT_ID`) have no `DEFAULT` clause at all — so "avoid function-valued defaults" was never an available fix. Confirmed at P1 by reading the actual schema file, then confirmed again structurally at P2 (ADR context): the real cause is a DuckDB-internal limitation replaying *any* pending `ALTER TABLE ADD COLUMN` WAL entry (`ReplayAlter`), regardless of whether it has a default. The actual fix (req-003) is to checkpoint immediately after any migration, so the ALTER is never left pending replay — worth remembering if a future migration's WAL-safety is in question: the fix is checkpoint timing, not avoiding `DEFAULT`.
- **`launchd`'s `KeepAlive.SuccessfulExit: false` and `systemd`'s `Restart=on-failure` already restart only on a non-zero exit** — the P0-time assumption that "refuse to start is unachievable from the daemon's exit code alone" (decision C) turned out to be based on an incomplete reading of both supervisors' actual semantics. Confirmed by reading `launchd.plist(5)`/`systemd.service(5)` behavior directly at P2 (ADR-030) and then empirically: `src/db/refuse-to-start.ts`'s `exit(0)` needed no plist/unit change to correctly "stay stopped" under either platform's existing, unmodified config. The originally-scoped supervision config changes (req-005) still shipped, re-scoped as defense-in-depth (ADR-031) rather than the primary mechanism — decision C's deliverable was honored, its stated reasoning was corrected.
- **`src/cli.ts`'s pre-existing `runDoctor()` already opens a second, independent DuckDB connection** (its write-test check, predates this feature) — confirmed at P1 to be capable of failing/blocking under DuckDB's single-writer lock while the daemon holds it. req-007's backup-staleness check deliberately never opens `telemetry.db` for this reason, reading a sidecar JSON file instead — worth remembering if a future `doctor` check is tempted to open the live database directly.
- **Reproducing the poisoned-WAL test fixture required *not* calling DuckDB's `disconnectSync()`/`closeSync()` cleanly** — a clean close auto-checkpoints and erases the exact condition under test. Also, `tsx`'s CLI re-execs into a child process, so a test harness killing only the directly-spawned PID orphans the real DuckDB-holding worker (and its file lock); `tests/integration/support/server-lifecycle-harness.ts` spawns `detached: true` and kills the whole process group for this reason. Worth knowing for any future test that needs to simulate an unclean daemon kill.
